# Jelly 语义行动层方向备忘

> 日期：2026-08-12
>
> 状态：后续方向备忘；不进入本轮基础编辑器实现与验收
>
> 来源讨论：ChatGPT 会话 `6a7c7151-62d0-83ea-9650-03db8a2cdac6`（“滴答清单设计哲学”）

## 1. 为什么记录这件事

滴答清单的 Note 并不是与任务系统隔绝的纯文档。笔记仍可拥有日期、提醒、标签和模板；快速输入中的自然语言时间也可能被识别成结构化属性。这说明它的核心设计不是“笔记里能写多少种内容”，而是：

> 任何信息都有可能进入行动和时间管理系统。

这个方向与 Jelly 的“灵感、笔记、Task Block、日历”关系很近，但不属于当前基础编辑器优化。当前优先级仍然是先让用户低成本、连续、可靠地把内容写下来。

## 2. Jelly 应该学什么，不应该直接复制什么

值得学习的不是某一种日期解析规则，而是从自然语言到行动的短路径：

`自然语言 → 发现潜在结构 → 建立行动关系`

不应直接复制“识别到日期就自动改数据”的做法。自动解析很快，但也可能误判普通词语，系统会在用户没有明确确认时替用户做决定。

Jelly 更合适的原则是：

1. 先完整保留用户原文。
2. 只把日期、任务、人物、链接、目标、子任务等识别为“候选结构”。
3. 用轻量、可忽略的方式呈现建议。
4. 用户确认后才建立 Task Block、日历或其他领域关系。
5. 用户拒绝或忽略时，不反复打扰，不偷偷改写内容。

一句话概括：

> 系统负责看见可能性，用户负责作决定。

## 3. 与现有 Jelly 能力的关系

Jelly 已经有一条可复用的产品链路：

`Note → Block → Task Block → Calendar Item`

后续自然语言识别应成为这条链路的输入加速器，而不是另起一套任务或日历数据模型。

例如用户写下：

> - [ ] 周五之前完成 Jelly 编辑器验收

系统可以识别：

- `[ ]` 是显式任务意图；
- “周五之前”是时间候选；
- 在该 Task Block 旁显示“周五 · 安排”；
- 只有用户点击确认后，才建立 `TaskBlockCalendarLink`。

这样既缩短了从记录到行动的路径，也保留了 Jelly 本地优先、可控、可恢复的特点。

## 4. 未来的产品边界：语义行动层

后续不应把每一种智能能力直接塞进编辑器：

`Editor → Date Parser → Calendar`

更合理的产品边界是：

`Editor → Semantic Suggestions → 用户确认 → Workspace Domain`

其中 Semantic Suggestions 可以逐步覆盖：

- 日期与时间候选；
- Task、Subtask 与 Goal 候选；
- 人物、链接和“以后看”等意图；
- 一段描述拆成多个 Task Block；
- 选中文字与 AI 讨论后产生的可执行建议。

这个“语义行动层”首先是产品边界，不是要求现在预建一套抽象框架。等真实功能启动时，再根据最小纵向闭环确定协议和实现，不为未来假设提前堆基础设施。

## 5. 一个更远的例子

用户写下：

> 这周把 Jelly V1 收尾，主要还有编辑器交互、灵感捕获和真实 GUI 验收，最好周五前完成。

后续 Jelly 可以识别出：

- Goal：Jelly V1 收尾；
- 潜在 Task Blocks：编辑器交互、灵感捕获、GUI 验收；
- 时间约束：周五前。

界面只给出“拆成 3 个任务”之类的建议。用户确认后，普通文本才转成 Task Blocks；每个 Task Block 再按需安排到日历。

## 6. 建议的演进顺序

1. 先把基础编辑体验做到滴答清单级别的轻、快、稳。
2. 做“选中文字与 AI 讨论”，验证建议如何出现、确认和撤销。
3. 做“任务描述 → Task Blocks”的最小纵向闭环。
4. 再把时间候选接入 `Task Block → Calendar`。
5. 只有多类建议都被真实使用后，再判断是否需要统一的语义行动协议。

## 7. 启动这个方向前必须重新确认的问题

- 日期建议是行内出现、块旁出现，还是统一进入上下文工具条？
- 建议被忽略后多久可以再次出现，如何避免提示疲劳？
- 原文、建议和确认后的结构如何共同参与撤销与恢复？
- 普通段落能否直接安排时间，还是必须先显式转成 Task Block？
- 灵感中的语义建议与笔记中的建议是否使用同一套交互？
- 哪些能力依靠确定性规则，哪些才值得调用模型？
- 本地优先场景中，模型不可用时编辑器是否完全不受影响？

以上问题没有通过真实原型和使用测试确认前，不进入架构承诺。
